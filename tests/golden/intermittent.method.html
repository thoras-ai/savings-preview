How the savings are computed

Per workload, per step, for CPU and memory separately
  1. Total each workload’s usage and requests across its replicas at every step, for CPU and for memory. A container counts at a step only when it has CPU and memory usage there; one without them, such as an init container or a check that runs now and then, is not running and adds no usage and no request.
  2. Take the highest usage in the trailing 15-minute window. The target is 1.1 × that peak.
  3. Waste at each step is max(0, requested − target). A request below the target is left alone; the report never adds.
  4. Price a core-hour and a GiB-hour from the default node, 4 cores, 16 GiB, $0.192 per hour, since the file has no node with a known list price: $0.048 per core-hour and $0.012 per GiB-hour.
  5. A workload’s hourly cost is max(CPU cost, memory cost): whichever resource runs out first decides how many nodes it needs. Current cost uses the request; optimized cost uses min(request, target).
  6. Average over the window, weighting each point by its step, and multiply by 8,760 hours. Savings is current minus optimized. The cluster figure is the sum over counted workloads.

What this is not

  • Not a forecast. Thoras forecasts the next 15 minutes; this report uses the peak that actually happened, so it is what right-sizing would have done over the window.
  • Not horizontal scaling. Replica counts are taken as they were. HPA and external metrics are out of scope.
  • Not realized savings. Freed requests reduce the bill only when nodes are removed; see Cluster and nodes.
  • Not your negotiated prices. Nodes are priced at list prices, on-demand or spot; set your own rates under Assumptions.
